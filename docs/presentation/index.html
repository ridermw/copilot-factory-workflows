Building the system that prompts the agent, so you stop being the one who does.

One engineer rewrote 535,000 lines of Zig into Rust in eleven days

WHAT

Bun — a JavaScript runtime. 1,448 files, 535,496 lines of Zig. A +1,000,000 line pull request.

HOW LONG

11 days. One engineer. About 50 dynamic workflows. Their own estimate for a team doing it by hand: a year.

THE PART THAT SHOULD BOTHER YOU

It shipped. It runs Claude Code today. Startup got 10% faster and “barely anyone noticed.”

Independent check: Prisma tested the rewrite against the production failures breaking their own platform — a memory leak that OOM-killed containers, and a connection pool that silently died after resume. Both fixed. They launched their public beta on it.

Disclosure, theirs and mine: Bun is owned by Anthropic, the author works there, and he used a pre-release model. Every number here is published and checkable, which is why I am using it.

Every shift starts with amnesia

“Imagine a software project staffed by engineers working in shifts, where each new engineer arrives with no memory of what happened on the previous shift.

One-shotting

Does everything at once, runs out of context mid-feature, and leaves the next session guessing.

Premature completion

A later session sees progress was made and declares the job done. Compaction fixes neither — it “doesn’t always pass perfectly clear instructions to the next agent.”

Each missing move has a name

NO VERIFICATION

The Nodding Loop. Ships whatever it produced — “an agent nodding at itself.”

NO PERSISTENCE

The Amnesiac Loop. Every run starts from zero.

NO SCHEDULING

The Manual Loop. One run you did once, not a loop.

NO DISCOVERY

The Blind Loop. Flawless execution on work that did not matter.

NO HANDOFF

The Tangled Loop. Agents colliding in the same files.

Bun’s structural rule: 1 implementer, 2 or more adversarial reviewers. “The implementer doesn’t review. The reviewer doesn’t implement.” The reviewer is given only the diff, and told to assume the code is wrong.

“Where one draws that line decides whether the loop is reliable”

Three bugs the adversarial reviewers caught. All three compiled cleanly.

ASYNC CLOSE

uv_close is asynchronous — libuv holds the pointer until the next tick, but the Box drops at the end of the match arm. Use-after-free, then double-free.

NEGATIVE TIMESPEC

For a file modified before 1970, trunc rounds toward zero and produces a negative nanoseconds field. floor keeps it in range.

EAGER UNWRAP

unwrap_or evaluates its argument eagerly, so the fallback panics before it can be ignored. unwrap_or_else stays lazy.

The reviewer’s context was only the diff, and it was told to assume the code was wrong. Every fix commit carries its review attribution in the subject line.

Bun’s version: when agents started stubbing out functions and writing long comments to justify workarounds, the fix was one new rule handed to the reviewers — “If you need a paragraph-long comment to justify why the workaround is OK, the code is wrong — fix the code.” One prompt edit, and it stopped.

The reorganization in one line: budget stops scaling with lines written and starts scaling with decisions made

MeasuredCost
One live status artifact, kept updated by a dedicated subagent~90k+ tokens

Tier the models: cheap workers for high-volume implementation, your best model for reviewers “and for anything that writes rules other agents will follow.” Figures are single-run observations, not benchmarks.

Four costs that accrue in silence

VERIFICATION DEBT

Saved time becomes unverified output, hiding “in the gap between ‘runs’ and ‘right’.”

Guard: an independent evaluator.

COMPREHENSION ROT

“The codebase grows while the map in one’s head stalls.”

Guard: read the output; explain a few changes.

COGNITIVE SURRENDER

Not “no time” but “no longer want to bother.”

Guard: the loop can execute, it cannot decide.

TOKEN BLOWOUT

“One bug can spin idle all night.”

Guard: hard caps before shipping.

“The more cheerfully it runs, the more quietly it errs”

Twenty PRs open overnight, all tests green. Three contain a subtle error the tests do not cover. No independent evaluator, so they merge. Twenty merged unread, so your model of the codebase lags by twenty changes. It went so smoothly, so you stop reading tomorrow’s batch. Helpers and retries ran free all night, so the bill is triple.

Three buried errors, in a codebase you no longer understand, guarded by someone who has stopped looking

The dangerous part is the same spot

“The most fascinating thing about loop engineering is that it lets one person do a team’s work. The most dangerous thing is the same spot — because a team argues with itself, and one person plus a pile of loops easily becomes an echo chamber where no one argues.

On the newer model they deleted context resets and the sprint construct entirely, and the builder ran coherently for over two hours without them. The planner survived — without it “the generator under-scoped.”

One loop, one week

1 · PICK THE REPEAT

The manual follow-up you did most often this week. That repeated step is a loop asking to be built.

2 · WRITE THE CHECK FIRST

Run it against deliberately broken input. If it passes, it is not a check.

3 · SEPARATE THE CRITIC

Adversarial review, rubber duck, or spar — in a different agent. Never self-review.

Cap the budget before you ship it
